# M4 连续状态存储完成报告

## 结论

M4-001、M4-002 已完成首版实现。存储层支持内存测试和 JSON 文件持久化，并已接入微信 Claw Bot 的文字打卡入口。

## 交付内容

### 状态模型

- `UserProfile`：用户标识、展示名、压力源、加入日期、陪伴阶段、安全等级。
- `ScreeningResult`：按 `recordedOn` 保存的压力初筛结果。
- `CheckInRecord`：按 `date` 保存的睡眠、情绪、压力和任务完成摘要。
- `PlanVersion`：以 `versionId` 区分多次 7 天游程，保留计划日和任务状态。
- `StoredSupportState`：按用户聚合上述必要状态。

### 行为

- 同一用户同一天初筛/打卡重复提交时覆盖旧记录，避免重复数据。
- 计划版本按版本 ID 独立保存，任务状态更新只影响目标版本和目标日期。
- 日期查询为闭区间，支持 M6 读取任意阶段数据。
- `deleteUserData` 删除用户全部 M4 状态。
- 文件写入先写临时文件，再原子替换目标文件；读写失败抛出 `SupportStorageException`。
- 微信 Bot 可通过 `开始打卡`、`打卡 ...`、`查看打卡` 触发 M4。

## 验收映射

| 分工要求 | 实现/证据 |
| --- | --- |
| 多日记录按日期查询 | `findCheckIns(userId, from, to)`；测试覆盖两天数据 |
| 区分计划版本 | `PlanVersion.versionId`；测试确认 `v1` 与 `v2` 状态隔离 |
| 重复打卡幂等 | `saveCheckIn` 按日期 upsert；测试确认只保留最新摘要 |
| M1/M3/M6 不依赖 DB | `SupportStateStore` 接口 |
| 数据库不可用有明确错误 | `SupportStorageException`；文件实现捕获 IO 失败 |
| 内存实现独立测试 | `InMemorySupportStateStore` |
| 重启恢复 | `FileSupportStateStore` 重新实例化测试 |
| 敏感数据策略 | 本报告“数据策略”及 `HANDOVER.md`：不保存原始语音/全文，提供删除入口 |
| 微信 Bot 可测试 | `WechatSupportCheckInServiceTest`；适配已挂到 `WechatMessageHandler` |

## 测试

测试类：`SupportStateStoreTest`

覆盖四组场景：幂等和日期查询、计划版本隔离、文件重启恢复、删除和非法输入。全量测试结果以 `docs/LOG.md` 最终记录为准。
